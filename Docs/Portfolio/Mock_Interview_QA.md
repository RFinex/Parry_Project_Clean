# 게임 클라이언트 개발자 모의 면접 답변 정리

> 사진에 나온 C#, Unity, 포트폴리오, 기타 질문을 기준으로 정리한 답변 초안입니다. 기술 질문은 정의와 차이를 설명하는 형태로 작성했습니다. 개인 이력에 관한 항목은 사실을 확인할 수 없는 부분을 `[직접 입력]`으로 표시했습니다. 본인 경험과 다른 내용은 면접 전에 반드시 수정하세요.

## 1. C#

### 1. OOP 프로그래밍이란

면접 답변 예시: “객체 지향 프로그래밍은 프로그램을 객체 단위로 나누어 설계하는 방식입니다. 객체는 데이터와 그 데이터를 다루는 기능을 함께 가집니다. 주요 특징은 캡슐화, 추상화, 상속, 다형성입니다. 캡슐화는 객체의 데이터를 외부에서 직접 바꾸지 못하게 하고, 정해진 기능을 통해서만 변경하도록 하는 것입니다. 예를 들어 체력 값을 외부에서 임의로 덮어쓰지 않고 피해를 받는 메서드로 변경하면, 체력이 음수가 되지 않도록 객체 안에서 검사할 수 있습니다. 추상화는 사용하는 쪽에 필요한 기능만 보여주고 내부 처리 방법은 감추는 것입니다. 예를 들어 이동 기능을 호출하는 쪽은 이동 방법의 세부 계산을 몰라도 됩니다. 상속은 기존 클래스의 공통 데이터와 기능을 물려받아 새 클래스를 만드는 것입니다. 여러 적이 공통으로 가진 체력 처리를 부모 클래스에 두고, 적마다 다른 공격 기능은 각 자식 클래스에 둘 수 있습니다. 다형성은 같은 부모 타입이나 인터페이스로 기능을 호출해도 실제 객체에 따라 다른 구현이 실행되는 것입니다. 예를 들어 여러 적을 같은 타입으로 다루면서 각 적의 공격 메서드는 자기 방식대로 실행할 수 있습니다. 이런 특징을 적절히 활용하면 공통 기능과 개별 기능을 구분하고, 변경이나 추가가 필요한 부분을 관리하기 쉬워집니다.”

### 2. 절차지향과 객체지향 비교

면접 답변 예시: “절차지향은 프로그램이 어떤 순서로 일을 처리할지 함수 중심으로 구성하는 방식입니다. 객체지향은 데이터와 그 데이터를 다루는 기능을 객체 안에 함께 두고, 객체들이 서로 기능을 요청하며 동작하도록 구성합니다. 절차지향은 처리 순서가 단순한 경우 이해하기 쉽고, 객체지향은 상태와 기능을 역할별로 나누고 싶을 때 관리하기 편합니다. 실제 프로그램에서는 두 방식을 함께 사용할 수 있습니다.”

### 3. C#의 struct와 class의 설명과 차이점

면접 답변 예시: “`struct`는 값 타입이고 `class`는 참조 타입입니다. struct 변수끼리 대입하면 값이 복사됩니다. class 변수끼리 대입하면 객체 자체가 복사되는 게 아니라 같은 객체를 가리키는 참조가 복사됩니다. 그래서 class는 한쪽 변수로 객체를 바꾸면 다른 쪽에서도 바뀐 내용이 보일 수 있습니다. 작고 독립된 값은 struct, 여러 기능이 참조하고 상태를 관리해야 하는 객체는 class로 두는 경우가 많습니다. 다만 struct는 항상 스택, class는 항상 힙에 저장된다고 말하면 정확하지 않습니다.”

### 4. 값 타입과 참조 타입의 차이

면접 답변 예시: “값 타입은 변수에 값이 복사되고, 참조 타입은 객체를 가리키는 참조가 복사됩니다. 예를 들어 정수 변수 하나를 다른 변수에 대입한 뒤 한쪽 숫자를 바꿔도 다른 숫자는 그대로입니다. 반면 같은 캐릭터 객체를 가리키는 변수가 두 개라면 한 변수를 통해 체력을 바꿨을 때 다른 변수로 봐도 바뀐 체력이 보입니다. 다만 참조 타입도 메서드에 전달될 때 기본적으로 참조값이 복사되어 전달된다는 점은 구분해야 합니다.”

### 5. GC에 대한 설명

면접 답변 예시: “GC는 프로그램에서 더 이상 사용할 수 없는 객체를 찾아 메모리를 정리하는 기능입니다. 객체를 가리키는 참조가 모두 끊겨 프로그램 어디에서도 그 객체를 찾을 수 없으면, GC가 나중에 정리할 수 있는 대상이 됩니다. 참조 하나를 `null`로 바꾼다고 바로 정리되는 것은 아니고, 다른 곳에서도 그 객체를 참조하고 있지 않아야 합니다. 또 정리 시점은 런타임이 정하므로 참조가 끊긴 즉시 실행된다고 보장할 수 없습니다. 메모리를 자동으로 정리해주는 장점이 있지만, 정리하는 동안 CPU 작업이 생겨 순간적으로 게임이 끊길 수 있습니다. 그래서 자주 실행되는 코드에서 불필요한 객체를 반복 생성하지 않도록 하고, Profiler로 할당과 GC 발생 여부를 확인합니다.”

### 6. 메모리 공간 설명(힙, 스택 영역 등)

면접 답변 예시: “스택은 메서드가 실행되는 동안 필요한 정보를 임시로 쌓아 두는 공간입니다. 메서드 실행이 끝나면 그 정보도 함께 정리됩니다. 힙은 프로그램 실행 중 만들어진 객체를 보관하는 공간입니다. 힙의 객체를 더 이상 어디에서도 참조하지 않으면 GC가 나중에 정리할 수 있습니다. 다만 값 타입은 항상 스택, 참조 타입은 항상 힙에 저장된다고 단정할 수는 없습니다. 값 타입도 다른 객체의 데이터로 들어가면 힙 안에 저장될 수 있습니다. 그래서 두 타입의 차이는 저장 위치보다 복사되는 방식과 참조되는 방식으로 설명하는 것이 좋습니다.”

### 7. 오버로딩과 오버라이딩 설명

오버로딩은 같은 이름의 메서드를 매개변수 개수나 타입을 다르게 정의하는 것입니다. 컴파일 시점에 전달한 인자에 맞는 메서드가 선택됩니다. 오버라이딩은 상속받은 가상 메서드의 구현을 파생 클래스에서 재정의하는 것이며, 실행 시점의 실제 객체 타입에 따라 호출 구현이 결정됩니다.

### 8. 제네릭 설명

제네릭은 타입을 매개변수로 받아 여러 타입에 재사용할 수 있는 클래스, 메서드, 인터페이스를 만드는 기능입니다. 예를 들어 `List<int>`와 `List<string>`은 같은 `List<T>` 구현을 각각 정수와 문자열에 적용합니다. 컴파일 시 타입 검사를 받을 수 있고, 비제네릭 컬렉션에서 값 타입을 object로 변환할 때 생기는 박싱을 피하는 데도 도움이 됩니다.

### 9. Interface와 추상클래스의 차이

인터페이스는 타입이 제공해야 하는 계약을 정의하고, 클래스는 여러 인터페이스를 구현할 수 있습니다. 추상 클래스는 공통 상태나 기본 구현을 함께 제공하면서 일부 동작을 파생 클래스에 맡길 수 있고, 클래스는 하나의 클래스만 상속할 수 있습니다. 공통 구현과 상태를 공유할 필요가 있으면 추상 클래스를, 서로 다른 타입에 공통 기능 계약을 적용하려면 인터페이스를 선택합니다.

### 10. List 설명(내부 동작 원리까지)

면접 답변 예시: “`List<T>`는 내부에 배열을 가지고 있고, 요소를 순서대로 저장합니다. 인덱스로 몇 번째 요소를 가져오는 것은 빠릅니다. 그런데 배열 공간이 꽉 찬 뒤 새 요소를 추가하면 더 큰 배열을 만들고 기존 값을 옮겨야 해서 그 순간 비용이 발생합니다. 중간에 값을 넣거나 빼도 뒤에 있는 요소들을 이동해야 합니다. 요소 수를 대략 알면 처음에 용량을 설정해 배열이 자주 커지는 일을 줄일 수 있습니다.”

### 11. 스택/큐 설명

스택은 후입선출(LIFO) 구조로 마지막에 넣은 값을 먼저 꺼냅니다. 함수 호출, 되돌리기, 깊이 우선 탐색 등에 쓸 수 있습니다. 큐는 선입선출(FIFO) 구조로 먼저 넣은 값을 먼저 꺼내며, 작업 대기열이나 너비 우선 탐색에 적합합니다.

### 12. 딕셔너리에 대한 설명(가능하다면 내부 동작 원리까지)

면접 답변 예시: “`Dictionary`는 키를 넣으면 그 키에 대응하는 값을 찾을 수 있는 자료구조입니다. 내부에서는 키의 해시값을 이용해 저장할 위치를 빠르게 찾고, 같은 위치를 가리키는 키가 있으면 실제 키가 같은지 추가로 비교합니다. 그래서 평균적으로 조회가 빠르지만, 충돌이 많으면 비교할 일이 늘어날 수 있습니다. 딕셔너리에 넣은 키의 값이 나중에 바뀌어 해시 계산 결과가 달라지면 찾지 못할 수 있으므로, 키로 쓰는 값은 안정적으로 유지해야 합니다.”

### 13. 해시테이블 설명

해시 테이블은 키를 해시 함수에 넣어 배열의 위치를 계산하고, 그 위치에 키와 값을 저장하는 자료구조입니다. 서로 다른 키가 같은 위치를 계산하는 해시 충돌이 발생할 수 있어 별도의 충돌 처리와 키 동등성 확인이 필요합니다. 해시 함수가 고르게 분포하고 충돌이 적으면 조회·삽입·삭제를 평균적으로 빠르게 처리할 수 있습니다.

#### 13-a. 해시충돌 설명 및 해결법

해시 충돌은 서로 다른 키가 같은 해시 버킷이나 인덱스를 가리키는 상황입니다. 대표적인 해결 방식은 같은 버킷에 여러 항목을 연결해 보관하는 체이닝과, 다른 빈 슬롯을 찾아 저장하는 개방 주소 방식입니다. .NET `Dictionary`는 버킷과 엔트리 구조를 사용해 충돌을 처리하고 키의 동등성을 확인합니다.

### 14. 그 외 사용해 본 자료구조(컬렉션)에 대한 설명

배열은 크기가 고정된 연속 요소 저장소로 인덱스 접근이 빠릅니다. `List<T>`는 배열을 기반으로 크기를 동적으로 관리합니다. `Dictionary<TKey, TValue>`는 키 조회에, `HashSet<T>`는 중복 없는 값 보관과 포함 여부 확인에 적합합니다. `Queue<T>`와 `Stack<T>`는 각각 선입선출과 후입선출 처리를 제공합니다. 자료구조는 이름보다 필요한 연산과 데이터 특성에 맞춰 선택합니다.

### 15. 콜 바이 밸류 / 콜 바이 레퍼런스 설명

값에 의한 전달은 인자의 값이 매개변수로 복사됩니다. 참조 타입을 값으로 전달하면 객체 자체가 복사되는 것이 아니라 객체 참조가 복사되므로, 메서드 안에서 객체 상태를 바꾸면 호출자에게도 보입니다. `ref`와 `out`은 변수 자체를 참조로 전달해 메서드가 호출자의 변수에 새 값을 대입할 수 있게 합니다. C#의 일반 매개변수 전달은 기본적으로 값에 의한 전달입니다.

### 16. 박싱/언박싱 설명

면접 답변 예시: “박싱은 정수 같은 값 타입을 `object`처럼 참조 타입으로 다루기 위해 객체 안에 감싸는 과정입니다. 언박싱은 그 객체에서 원래 값 타입을 다시 꺼내는 과정입니다. 박싱이 일어나면 값을 복사하고 관리 힙 객체가 생길 수 있어 반복적으로 발생하면 할당이 늘어납니다. 그래서 컬렉션이나 메서드를 만들 때 가능하면 `object` 대신 제네릭 타입을 사용하면 불필요한 박싱을 줄일 수 있습니다.”

### 17. 얕은복사/깊은복사 설명

얕은 복사는 객체의 바깥쪽 값만 복사하고, 안에 들어 있는 객체는 원본과 복사본이 함께 사용하게 하는 방식입니다. 그래서 복사본에서 안쪽 객체의 값을 바꾸면 원본에서도 바뀐 값이 보일 수 있습니다. 깊은 복사는 안에 들어 있는 객체까지 새로 만들어 복사본이 원본과 따로 동작하게 합니다. 복사한 뒤 원본과 복사본이 같은 데이터를 함께 써도 되는지에 따라 방식을 선택합니다.

### 18. 업캐스팅/다운캐스팅 설명

업캐스팅은 자식 클래스 객체를 부모 클래스나 인터페이스 타입으로 다루는 것입니다. 여러 종류의 객체를 공통된 방식으로 관리할 때 편리합니다. 다운캐스팅은 부모 타입으로 다루던 객체를 다시 특정 자식 타입으로 바꾸는 것입니다. 실제 객체가 그 자식 타입이 아닐 수도 있으므로, 변환하기 전에 `is`나 패턴 매칭으로 타입을 확인하는 것이 안전합니다.

### 19. 동기/비동기 설명

동기 처리는 한 작업이 끝날 때까지 다음 작업을 시작하지 않습니다. 비동기 처리는 시간이 걸리는 작업을 기다리는 동안 다른 일을 계속할 수 있게 합니다. 비동기라고 해서 반드시 다른 스레드에서 실행되는 것은 아닙니다. Unity에서는 일정 시간이나 작업 결과를 기다리면서도 메인 스레드를 멈추지 않고, 기다림이 끝난 뒤 다음 처리를 이어갈 수 있습니다.

### 20. Static 설명
Static은 변수나 함수, 클래스에 정적 속성을 부여하는 것으로 클래스로부터 객체를 생성하지 않고 변수나 함수를 호출할 수 있도록 해주는 것입니다.
`static`은 값이나 기능이 각각의 객체가 아니라 클래스 자체에 속한다는 뜻입니다. 객체를 만들지 않아도 사용할 수 있고, 정적 변수는 모든 객체가 하나를 함께 사용합니다. 공통으로 쓸 기능이나 값을 두기 편하지만, 여러 곳에서 값을 바꾸면 변경 위치를 찾기 어려워질 수 있습니다. 꼭 함께 써야 하는 경우에 사용하는 것이 좋습니다.

### 21. Class 생성자/소멸자 설명

생성자는 객체가 만들어질 때 필요한 값을 넣고 처음 상태를 준비하는 기능입니다. 클래스 이름과 같은 이름을 사용하며, 입력값이 다른 생성자를 여러 개 만들 수도 있습니다. C#의 소멸자는 객체가 정리되는 시점을 직접 정하지 못하고, GC가 언제 실행될지도 보장되지 않습니다. 그래서 파일이나 연결처럼 정리 시점이 중요한 자원은 `Dispose` 같은 방법으로 직접 정리합니다.

### 22. 콜백 설명

콜백은 어떤 일이 끝났을 때 실행하도록 미리 전달해 둔 함수입니다. 예를 들어 버튼을 눌렀을 때 실행할 기능이나, 작업이 끝난 다음 이어서 할 일을 콜백으로 지정할 수 있습니다. 함수를 전달받은 쪽은 정해진 시점에 그 함수를 실행해 다음 작업을 이어갑니다. 콜백이 여러 단계로 이어지면 실행 순서를 따라가기 어려울 수 있으므로, 각 콜백의 역할과 실행 시점을 분명하게 관리해야 합니다.

### 23. LINQ 설명

LINQ는 목록에서 필요한 항목을 찾거나, 항목의 값을 바꾸거나, 순서를 정리할 때 사용하는 기능입니다. `Where`는 조건에 맞는 항목을 고르고, `Select`는 각 항목을 원하는 값으로 바꾸며, `OrderBy`는 순서대로 정리합니다. 코드를 짧게 쓸 수 있지만, `ToList`나 `ToArray`를 사용하면 결과를 담을 새 목록이나 배열이 만들어집니다. 자주 실행되는 코드에서는 불필요한 메모리 사용이 생기지 않는지 확인하는 것이 좋습니다.

### 24. 문자열 할당 시 메모리는 어떻게 사용되는가?

문자열의 글자 데이터는 관리 힙에 문자열 객체로 저장됩니다. 문자열 변수에는 보통 그 객체를 가리키는 참조가 들어갑니다. 문자열은 한 번 만들어지면 내용을 직접 수정할 수 없는 불변 객체입니다. 예를 들어 두 문자열을 연결하면 기존 문자열의 내용이 바뀌는 것이 아니라, 연결한 내용을 담은 새 문자열 객체가 관리 힙에 만들어집니다. 기존 문자열은 그대로 남아 있으며, 더 이상 어떤 변수나 객체에서도 참조하지 않을 때 GC가 나중에 정리할 수 있습니다. GC는 참조가 끊기는 즉시 실행되는 것이 아니므로, 반복문에서 매번 문자열을 연결하면 중간 문자열 객체가 쌓여 메모리 할당과 이후 정리 부담이 커질 수 있습니다.

#### 24-a. 대처방법은? (`StringBuilder`를 찾아보자)

문자열을 몇 번만 연결한다면 일반적인 문자열 연결이 간단하고 읽기 쉽습니다. 반면 반복문에서 많은 조각을 이어 붙여야 한다면 `StringBuilder`를 사용할 수 있습니다. `StringBuilder`는 관리 힙에 내부 버퍼를 두고, 문자열 조각을 그 버퍼에 차례로 추가하거나 수정합니다. 매번 연결 결과 문자열을 새로 만드는 대신 버퍼를 재사용하고, 작업이 끝났을 때 `ToString()`으로 최종 문자열을 만듭니다. 버퍼 공간이 부족하면 내부적으로 더 큰 공간을 마련할 수 있으므로, 문자열이 아주 크거나 자주 만들어지는 경우에는 예상 크기와 실제 할당을 확인하면 좋습니다.

### 25. Delegate 설명

delegate는 정해진 입력값과 반환값 형태에 맞는 함수를 담아 전달할 수 있는 타입입니다. 함수를 다른 코드에 넘기거나, 나중에 실행할 기능으로 보관할 때 사용합니다. `Action`은 결과를 돌려주지 않는 함수에, `Func`는 결과를 돌려주는 함수에 사용합니다. 이벤트도 delegate를 바탕으로 동작하며, 어떤 일이 일어났을 때 등록된 함수들에게 알립니다.

### 26. SOLID 설명

SOLID는 객체지향 코드를 이해하고 변경하기 쉽게 만드는 다섯 가지 설계 원칙입니다.

- **단일 책임 원칙(SRP):** 클래스 하나가 한 종류의 역할을 맡도록 합니다.
- **개방-폐쇄 원칙(OCP):** 새 기능을 추가할 때 기존 코드를 계속 고치지 않도록 구성합니다.
- **리스코프 치환 원칙(LSP):** 부모 객체를 호출하는 동작에서 자식 객체가 부모 객체를 완전히 대체할 수 있어야 합니다.
- **인터페이스 분리 원칙(ISP):** 인터페이스 하나에 여러 기능을 담지말고 잘게 나눠야 한다.
- **의존 역전 원칙(DIP):** 구체적인 구현 하나에 직접 묶이지 않고 공통 규칙을 통해 연결합니다.

이 원칙들은 무조건 적용하는 규칙이라기보다, 코드의 역할이 섞이거나 기능 간 연결이 복잡해질 때 설계를 점검하는 기준입니다.

### 27. C# 기준, 컴파일 과정 설명

C# 코드는 먼저 IL이라는 중간 코드로 변환됩니다. 프로그램을 실행할 때 이 코드는 컴퓨터가 처리할 수 있는 명령으로 바뀝니다. 실행 중 필요한 코드를 바꾸는 방식을 JIT, 실행 전에 미리 바꾸는 방식을 AOT라고 합니다. Unity에서는 설정에 따라 Mono 또는 IL2CPP를 사용할 수 있습니다.

#### 27-a. IL2CPP 설명

IL2CPP는 Unity에서 사용하는 실행 방식 중 하나입니다. Unity가 C# 코드에서 만들어진 IL을 C++ 코드로 바꾸고, 플랫폼에 맞는 컴파일러가 최종 실행 파일을 만듭니다. 실행 전에 코드를 변환하므로 실행 중에 코드를 바꾸기 어려운 플랫폼에서도 사용할 수 있습니다. 대신 빌드 시간이 길어질 수 있습니다.

### 28. 캐시메모리에 대해 설명

CPU 캐시는 CPU 가까이에 있는 작고 빠른 저장 공간입니다. CPU가 자주 쓰는 데이터나 그 주변 데이터를 잠시 보관해, 메인 메모리까지 매번 다녀오는 시간을 줄입니다. 배열처럼 데이터가 나란히 있으면 차례로 읽기 쉬워 캐시를 잘 활용할 수 있습니다. 데이터가 여러 곳에 흩어져 있으면 필요한 값을 찾느라 처리 시간이 늘어날 수 있습니다.

### 29. 프로세스와 스레드 설명

프로세스는 실행 중인 프로그램 하나가 사용하는 독립된 실행 공간입니다. 스레드는 그 안에서 명령을 처리하는 실행 흐름입니다. 한 프로세스 안에 여러 스레드가 있으면 메모리와 자원을 함께 사용할 수 있지만, 각자 따로 실행되기도 합니다. 여러 스레드가 같은 값을 동시에 바꾸면 결과가 꼬일 수 있어 접근 순서를 조정해야 합니다.

### 30. 사용해본 정렬 알고리즘 설명(선택, 버블, 퀵, 버블 등)

버블 정렬은 이웃한 두 값을 비교해 순서가 틀리면 자리를 바꾸는 방식입니다. 선택 정렬은 아직 정렬되지 않은 부분에서 가장 작은 값을 찾아 앞으로 옮깁니다. 퀵 정렬은 기준값을 정해 작은 값과 큰 값으로 나눈 뒤, 나뉜 부분을 다시 정렬합니다. 퀵 정렬은 보통 빠르지만 기준값을 계속 나쁘게 고르면 느려질 수 있습니다. 직접 구현한 경험이 없다면 원리를 아는 것과 실제 사용한 경험을 구분해 답합니다.

### 31. 통신에 대해 알고 있는지?(API, TCP/IP, UDP 등)

네트워크 통신은 프로그램끼리 데이터를 주고받는 것입니다. API는 다른 프로그램에 기능이나 데이터를 요청하는 약속된 방법입니다. TCP는 데이터가 순서대로 도착하고 전달되도록 확인하는 방식이라 웹이나 파일 전송 등에 많이 쓰입니다. UDP는 전달이나 순서를 확인하지 않는 대신 처리 부담이 적어, 빠른 전달이 중요한 실시간 통신에 사용할 수 있습니다. 직접 구현한 경험이 없다면 개념을 알고 있는 것과 프로젝트에서 사용한 것을 구분해 답합니다.

## 2. Unity

### 1. 라이프사이클에 대해 설명

Unity 생명주기는 오브젝트가 생성·활성화되고 프레임을 처리한 뒤 비활성화·파괴되는 과정에서 정해진 콜백이 호출되는 규칙입니다. 초기화에는 `Awake`, `OnEnable`, `Start`, 프레임 처리에는 `Update` 계열, 물리 처리에는 `FixedUpdate`, 정리에는 `OnDisable`, `OnDestroy` 등이 사용됩니다. 컴포넌트 활성화와 씬 전환에 따라 호출 조건이 다르므로 필요한 콜백의 의미를 구분해 써야 합니다.

### 2. Start와 Awake의 차이와 적절한 사용처
Awake는 프리팹이 인스턴스화 된 직후에 호출되는 함수이고 Start는 인스턴스 활성화 후 첫 프레임이 시작되기 전 호출되는 함수입니다.
Awake는 내부 컴포넌트를 미리 캐싱하고 초기화할 때 사용하고, Start는 모든 초기화가 끝난 후 로직을 실행할 때 사용하는 편이 적절하다고 생각합니다.
면접 답변 예시: “`Awake`는 컴포넌트가 로드될 때 초기화하는 함수이고, `Start`는 오브젝트가 활성화된 상태에서 첫 프레임이 시작되기 전에 한 번 호출됩니다. 그래서 자기 컴포넌트 안의 참조나 기본 상태를 준비할 때는 `Awake`를 쓰고, 다른 오브젝트들이 준비된 뒤 시작할 작업은 `Start`에 두는 편입니다. 단, 여러 오브젝트 사이의 초기화 순서가 꼭 필요하다면 `Awake`만 믿지 말고 실행 순서나 초기화 구조를 명확히 정해야 합니다.”

### 3. Update와 FixedUpdate의 차이와 적절한 사용처
Update는 매 프레임마다 실행되는 함수로 기기의 성능에 따라 호출 간격이 달라질 수 있습니다.
FixedUpdate는 고정된 시간 간격마다 실행되는 함수로 성능과 무관하게 동일한 간격으로 호출됩니다.
Update는 사용자의 입력감지나 타이머, 정보 갱신등에 주로 사용되며, FixedUpdate는 물리연산을 실행해야 할 때 사용됩니다.
면접 답변 예시: “`Update`는 화면 프레임마다 호출되기 때문에 호출 간격이 일정하지 않습니다. 입력 확인이나 UI처럼 화면과 함께 갱신할 작업에 씁니다. `FixedUpdate`는 정해진 시간 간격으로 실행되어 물리 시뮬레이션과 맞춰집니다. Rigidbody에 힘을 주는 동작은 보통 `FixedUpdate`에서 처리합니다. 입력은 `Update`에서 읽고, 다음 물리 업데이트에서 사용하도록 저장해 두는 식으로 나눌 수 있습니다.”

### 4. Unity GC에 대한 설명

면접 답변 예시: “Unity에서 C# 코드가 만드는 일반 객체는 관리 메모리에 할당되고, 더 이상 참조되지 않는 객체는 GC가 나중에 정리합니다. 프레임마다 문자열이나 임시 배열을 계속 만들면 정리할 객체가 쌓여 GC가 더 자주 일어날 수 있고, 그 순간 프레임이 끊길 수 있습니다. 또 `GameObject`나 `Component`는 C# 참조와 Unity 내부의 네이티브 객체가 함께 관련되므로, Destroy된 Unity 객체는 일반 C# 객체와 null 동작이 다르게 보일 수 있습니다. 그래서 할당이 문제인지 Profiler의 GC Alloc 등을 보고 확인합니다.”

### 5. 쿼터니언에 대한 설명(짐벌락 포함)

면접 답변 예시: “쿼터니언은 3D 회전을 표현하는 방식입니다. 오일러 각도처럼 X·Y·Z 회전값을 직접 더하는 방식은 직관적이지만, 특정 회전 상태에서 축이 겹쳐 한 축의 회전 자유도를 잃는 짐벌락이 생길 수 있습니다. 쿼터니언은 회전을 4개의 값으로 표현해 이런 짐벌락 문제를 피하고 회전 보간도 안정적으로 처리할 수 있습니다. 다만 값 자체는 직관적으로 읽기 어려워 Unity의 `Quaternion.Euler`, `Quaternion.LookRotation`, `Quaternion.Slerp` 같은 API로 다루는 경우가 많습니다.”

### 6. async await 키워드 설명

면접 답변 예시: “`async`는 메서드 안에서 비동기 대기를 할 수 있게 하고, `await`는 작업이 끝날 때까지 그 메서드의 다음 줄을 잠시 미뤘다가 완료되면 이어서 실행합니다. 메인 스레드를 그냥 멈춰 세우는 대기와는 다릅니다. 또 `async`를 붙였다고 자동으로 새 스레드가 생기는 것은 아닙니다. Unity API는 대부분 메인 스레드에서 사용해야 하므로, 백그라운드 작업과 Unity 오브젝트 접근을 구분해야 합니다.”

### 7. 코루틴 설명

면접 답변 예시: “코루틴은 여러 프레임에 걸친 동작을 순서대로 쓰기 편한 Unity 기능입니다. 예를 들면 일정 시간 기다린 뒤 애니메이션을 재생하거나, 몇 프레임에 걸쳐 연출을 진행할 수 있습니다. `yield` 위치에서 기다렸다가 다음 프레임이나 지정한 시점에 이어서 실행합니다. 별도 스레드에서 일하는 기능은 아니기 때문에 CPU를 많이 쓰는 계산을 자동으로 분산해 주지는 않습니다.”

### 8. 그 외 비동기 기능 사용해본 것 설명

Unity에서 코루틴 외에는 `Task`/`async`·`await`, Unity의 `Awaitable`, 그리고 UniTask 같은 라이브러리를 사용할 수 있습니다. UniTask는 Unity PlayerLoop에 맞춘 경량 비동기 타입을 제공하며 CancellationToken과 결합해 취소를 다루기 편합니다. 프로젝트나 Unity 버전에 따라 사용할 수 있는 API와 동작이 다르므로 사용 환경의 문서를 확인해야 합니다.

### 9. 코루틴과 Invoke 차이

`Invoke`는 메서드 이름을 문자열로 지정해 일정 시간 뒤 호출하는 간단한 지연 호출 기능입니다. 코루틴은 여러 대기 지점과 순차적인 흐름을 작성할 수 있고, 변수와 조건에 따라 대기 시간을 조절하기 쉽습니다. 단일 지연 호출은 `Invoke`, 복수 단계 연출이나 취소·조건 처리가 필요하면 코루틴 또는 비동기 작업이 더 적합할 수 있습니다. 문자열 기반 호출은 리팩터링과 컴파일 타임 오류 검출에 불리합니다.

### 10. Event, Action, Func 설명

면접 답변 예시: “delegate는 메서드를 담아 다른 코드에 전달할 수 있는 타입입니다. `Action`은 반환값이 없는 메서드를, `Func`는 값을 반환하는 메서드를 담을 때 씁니다. `event`는 알림을 구독하는 기능으로, 외부 코드는 구독과 해제는 할 수 있지만 이벤트를 직접 발생시키지는 못합니다. 구독이 끝났는데 해제를 빼먹으면 객체가 예상보다 오래 남거나 같은 알림이 여러 번 처리될 수 있어 생명주기에 맞춰 정리해야 합니다.”

### 11. 최적화에 대한 설명(CPU 최적화, GPU 최적화 등)

면접 답변 예시: “최적화는 먼저 어디가 느린지 확인하고 시작해야 합니다. 게임 로직이나 물리 계산 때문에 CPU가 바쁜지, 화면을 그리는 데 GPU가 바쁜지에 따라 해결 방법이 다릅니다. CPU 쪽은 반복 계산, 많은 Update, 메모리 할당과 GC 등을 보고, GPU 쪽은 화면에 그리는 오브젝트 수나 셰이더와 오버드로우 등을 봅니다. 코드를 짧게 바꾸는 것보다 같은 장면과 조건에서 측정해 실제로 나아졌는지 비교하는 게 중요합니다.”

### 12. 프로파일러에 대한 설명

면접 답변 예시: “Profiler는 게임이 실행되는 동안 어느 부분에 시간이 들고 메모리가 얼마나 할당되는지 보여주는 분석 도구입니다. CPU 화면에서는 어떤 함수가 오래 걸리는지 보고, 메모리 쪽에서는 객체 할당이나 GC가 일어나는지 확인할 수 있습니다. 측정 결과는 에디터 자체의 부하 영향을 받을 수 있어 실제 빌드와 대상 기기에서도 확인하는 게 좋습니다. 변경 전후를 비교할 때는 같은 장면과 같은 동작을 재현해야 결과를 믿을 수 있습니다.”

### 13. 배치/드로우콜 설명

드로우콜은 CPU가 GPU에 렌더링 작업을 제출하는 호출입니다. 드로우콜이 많으면 CPU 측 렌더링 제출 비용이 커질 수 있습니다. 배칭은 호환되는 오브젝트의 렌더링 작업을 묶어 드로우콜을 줄이는 기법으로, 정적·동적 배칭이나 GPU Instancing 등이 있습니다. 재질, 셰이더, 오브젝트 상태에 따라 배칭 조건이 달라지고, 배칭이 항상 성능을 개선하는 것은 아니므로 Frame Debugger와 Profiler로 확인합니다.

#### 13-a. 줄이기 위한 방법은?

같은 머티리얼과 텍스처를 공유하고, 호환되는 오브젝트를 배칭하거나 GPU Instancing을 적용할 수 있습니다. UI에서는 동일한 Canvas에 불필요하게 많은 분할이 생기지 않도록 하고, 머티리얼과 마스크 변경이 배칭을 깨는지 확인합니다. 오브젝트 수를 줄이거나 컬링을 활용하는 것도 도움이 됩니다. 구체적인 방법은 병목과 렌더 파이프라인에 따라 측정 후 선택합니다.

### 14. UI 최적화 방법 설명

UI 변경으로 Canvas 전체가 자주 다시 빌드되지 않도록 자주 바뀌는 요소와 정적인 요소를 적절히 분리합니다. 불필요한 레이아웃 그룹과 중첩 마스크를 줄이고, 비활성 UI는 상황에 맞게 비활성화하거나 화면 밖 렌더링을 피합니다. Canvas를 과도하게 쪼개면 오히려 드로우콜과 관리 비용이 늘 수 있으므로 UI Profiler에서 리빌드와 배칭을 확인하며 조절합니다.

### 15. 사용해 본 최적화 방법 설명

개인 프로젝트의 공격 탐색에서 `Physics2D.OverlapCircleAll`이 매 호출마다 결과 배열을 반환하는 점을 확인했습니다. `ContactFilter2D`와 재사용 `List<Collider2D>`를 사용하는 `Physics2D.OverlapCircle` 오버로드로 바꾸고, 리스트를 멤버로 유지해 매번 `Clear()` 후 재사용했습니다. 더미 적 30마리를 동일 위치에 겹쳐 배치한 같은 조건의 Profiler 비교에서 해당 탐색의 GC Alloc이 호출당 272B에서 0B가 됐습니다. 이 수치는 측정 조건에 한정해 설명합니다.

### 16. 오브젝트 풀링 설명 및 구현 방법

오브젝트 풀링은 자주 생성·파괴되는 객체를 미리 만들고 비활성 상태로 보관했다가 필요할 때 활성화해 재사용하는 기법입니다. 생성과 파괴 비용 및 관련 할당을 줄일 수 있습니다. 풀에서 꺼낼 때 위치·상태·이벤트 구독을 초기화하고, 반환할 때 트윈·코루틴·참조·상태를 정리해야 합니다. 프로젝트에서 사용했다고 말할 때는 실제 적용한 풀 대상과 반환 흐름을 구체적으로 설명합니다.

### 17. LOD 설명

LOD(Level of Detail)는 카메라와의 거리나 화면 기여도에 따라 오브젝트의 모델이나 표현 복잡도를 낮추는 기법입니다. 멀리 있는 물체에 단순한 메시를 사용해 GPU 렌더링 비용을 줄일 수 있습니다. 전환 거리와 단계 수를 잘못 잡으면 팝핑이 보이거나 메모리가 늘 수 있어 화면 품질과 성능을 함께 확인합니다. 2D 스프라이트 게임에서는 3D 메시 LOD가 직접 필요하지 않을 수 있습니다.

### 18. 오클루전 컬링 설명

오클루전 컬링은 다른 물체에 완전히 가려져 카메라에 보이지 않는 오브젝트의 렌더링을 생략하는 기법입니다. 카메라 프러스텀 밖 오브젝트를 제외하는 프러스텀 컬링과는 다릅니다. 차폐물과 장면 구조를 분석해 가려진 렌더러를 그리지 않아 GPU 작업을 줄일 수 있지만, 베이크나 런타임 계산 비용 및 메모리를 고려해야 합니다.

### 19. 어드레서블 설명

Addressables는 에셋을 주소로 참조하고 비동기적으로 로드·해제할 수 있게 해 주는 Unity 에셋 관리 시스템입니다. 에셋 의존성을 관리하고 로컬 또는 원격 콘텐츠 배포를 구성하는 데 활용됩니다. 로드한 핸들을 적절히 해제하고 그룹·카탈로그·빌드 설정을 관리해야 합니다. 사용 경험이 없다면 개념 설명과 실제 사용 경험을 구분합니다.

### 20. 사용해 본 디자인패턴 설명(싱글톤 제외)

디자인 패턴은 자주 나타나는 설계 문제에 대한 재사용 가능한 구조적 해법입니다. 예를 들어 Factory는 구체 타입 생성 책임을 한 곳에 모으고, Observer는 발행자와 구독자를 이벤트로 연결하며, Object Pool은 객체를 재사용합니다. 패턴 이름을 붙이는 것보다 어떤 문제를 해결했고 어떤 비용이나 제약이 생겼는지 설명하는 것이 중요합니다. 실제로 적용한 패턴만 경험으로 제시합니다.

### 21. 아는 디자인패턴 설명(싱글톤 제외, 쓴다면 어디에 쓰는지 포함)

Factory는 생성 대상 선택과 생성 로직을 호출부에서 분리합니다. Observer는 한 객체의 상태 변화를 여러 구독자에게 전달해 직접 참조를 줄입니다. State는 현재 상태에 따라 동작을 분리하고, Object Pool은 반복 생성·파괴 대신 객체를 재사용합니다. 어느 패턴이든 전역 참조, 추적 어려움, 초기화 비용 등 부작용이 있을 수 있어 필요한 범위에서 사용해야 합니다.

### 22. 길찾기 알고리즘 사용해 본 것 설명

길찾기는 그래프의 노드와 간선을 따라 시작점에서 목표점까지 경로를 찾는 문제입니다. BFS는 모든 간선 비용이 같을 때 최단 간선 경로를 찾고, Dijkstra는 음수가 아닌 가중치에서 비용 최단 경로를 찾습니다. A*는 실제 비용 `g`와 목표까지의 추정 비용 `h`를 더해 탐색 방향을 유도합니다. 고전적인 길찾기 알고리즘을 직접 사용하지 않았다면, 무작위 스테이지 경로 생성과 길찾기는 목적이 다르다고 구분해 답변합니다.

### 23. 렌더링 파이프라인 설명

렌더링 파이프라인은 장면의 카메라, 오브젝트, 조명, 재질 정보를 GPU가 화면 픽셀로 변환하는 처리 과정입니다. Unity에서는 렌더 파이프라인이 렌더러와 셰이더를 통해 어떤 패스를 어떤 순서로 실행할지 관리합니다. URP에서는 렌더러가 컬링 후 렌더러 목록을 만들고, 패스별로 오브젝트를 그려 최종 화면을 구성합니다. 구체적인 순서는 파이프라인과 렌더러 설정에 따라 다릅니다.

### 24. 데이터 저장 및 불러오는 방법 설명 및 사용해 본 것

데이터의 성격과 수명에 따라 저장 방식을 선택합니다. ScriptableObject는 Unity 프로젝트 안에서 공유하는 정적 설정·콘텐츠 데이터에 적합하고, JSON이나 바이너리 파일은 실행 중 변하는 사용자 저장 데이터에 활용할 수 있습니다. PlayerPrefs는 간단한 키-값 설정에 적합하지만 복잡하거나 중요한 저장 데이터를 담기에는 적절하지 않습니다. 외부 스프레드시트는 편집·밸런싱 원본으로 사용할 수 있고, 빌드에 필요한 형태로 변환·가져오는 단계를 둘 수 있습니다.

#### 24-a. JSON

JSON은 객체와 배열 형태로 데이터를 표현하는 텍스트 포맷입니다. 사람이 읽기 쉽고 여러 언어에서 지원해 설정이나 저장 데이터 교환에 편리합니다. C# 객체 직렬화와 역직렬화를 통해 사용할 수 있지만, 큰 데이터에서는 텍스트 파싱 비용과 파일 크기를 고려하고 저장 데이터 버전 변경도 처리해야 합니다.

#### 24-b. 엑셀/구글 시트 읽어오기

스프레드시트는 비개발자도 표 형식 데이터를 편집하기 쉬워 밸런스 데이터 관리에 유용합니다. 데이터를 읽을 때 시트 ID, 탭 이름, 열 이름, 자료형, 필수값을 검증하고, 오류 행을 알 수 있는 메시지를 제공해야 합니다. 빌드 중 직접 네트워크에서 읽는 방식인지 에디터에서 에셋으로 가져오는 방식인지 구분해야 합니다.

#### 24-c. SO로 저장

ScriptableObject는 Unity 에셋으로 저장되는 데이터 컨테이너입니다. 여러 오브젝트가 공유하는 설정을 에셋으로 참조할 수 있어 프리팹에 같은 데이터를 중복 저장하지 않아도 됩니다. 일반적으로 빌드 실행 중에는 에셋 원본을 저장 데이터처럼 변경하는 방식으로 쓰지 않고, 플레이어별로 변하는 상태는 별도의 런타임 객체나 저장 파일로 관리합니다.

### 25. 통신 사용해봤는지

실제 경험에 맞춰 답변해야 합니다. **직접 사용하지 않았다면:** “게임 네트워크 통신을 직접 구현한 경험은 없습니다. 다만 HTTP API는 요청과 응답으로 서버 기능을 호출하는 인터페이스이고, TCP와 UDP는 전송 특성이 다른 전송 계층 프로토콜로 이해하고 있습니다.” **사용했다면:** 사용한 프로토콜, 요청 흐름, 오류·재시도·시간 초과 처리, 본인이 맡은 범위를 구체적으로 설명합니다.

## 3. 포트폴리오

### 1. 게임의 핵심 기술에 대한 설명(기능 소개가 아닌 기술)

Shield Hero의 핵심 기술은 전투 판정과 상태 처리를 역할별로 나누고, 데이터를 별도 에셋으로 관리하며, 여러 시스템을 서로 연결한 방식입니다. 예를 들어 공격 정보는 판정에 필요한 값을 전달하고, 플레이어 전투 코드는 가드·패리 결과를 처리합니다. 유물 데이터는 ScriptableObject로 관리하고, 효과는 전투 이벤트를 통해 연결합니다. 단순히 “전투 기능을 구현했다”고 끝내기보다 데이터·판정·상태·이벤트가 연결되는 구조를 설명합니다.

### 2. 팀 프로젝트가 있다면

#### 2-a. 본인이 맡은 역할

5인 팀 프로젝트에서 날짜 시스템, 이벤트 시스템, 자동 생산 시스템, 디버그 도구를 담당했습니다. 특히 매니저 간 직접 참조가 늘어나는 문제를 줄이기 위해 공통 이벤트 관리 구조인 `GameEventBridge`를 제안하고 구현했으며, 팀원들과 이벤트 종류·전달 데이터·적용 순서를 맞췄습니다. 실제로 맡지 않은 작업까지 제 기여로 말하지 않겠습니다.

#### 2-b. 팀플에 문제가 있었다면? 해결한 방법은?

팀원의 프로젝트에서 에셋 문제가 발생했을 때, 문제 프로젝트와 정상 동작하는 제 프로젝트의 에셋 및 폴더 구성을 비교했습니다. 당연히 있을 것이라고 생각해 확인하지 않았던 Ignore 대상 폴더의 에셋 누락을 확인했고, 누락된 에셋을 보완하고 관리 기준을 팀원에게 공유했습니다. 문제를 해결할 때 익숙한 전제를 먼저 확정하지 않고 두 환경의 차이를 비교하는 것이 중요하다는 점을 배웠습니다.

### 3. OO 기능 구현 방법 설명

포트폴리오의 기능을 소개할 때는 사용한 기술 이름만 말하기보다, 입력이나 데이터가 어떤 판정을 거쳐 결과로 이어지는지 설명합니다. 아래 답변은 실제 구현에 맞춰 정리한 예시입니다.

#### 3-a. 가드·패리 판정은 어떻게 구현했나요?

“가드 입력은 `PlayerController.OnGuard`에서 받습니다. 입력이 시작되면 스태미나 파괴 여부와 가드 재사용 대기 상태를 확인하고, 플레이어 FSM을 `PlayerGuardState`로 전환합니다. 가드 상태에 들어가면 `PlayerCombat.GuardStart`가 방어 상태와 패리 상태를 켜고, `UniTask.Delay`로 `ParryTime`만큼 기다린 뒤 패리 상태만 종료합니다. 이 대기는 플레이어의 취소 토큰을 사용하므로 상태가 끝나면 함께 취소됩니다. 따라서 버튼을 누른 직후의 짧은 구간은 패리 판정이고, 그 시간이 지나도 버튼을 계속 누르고 있으면 일반 가드가 유지됩니다.

적 공격은 `EnemyAttackInfo`에 담긴 가드·패리 가능 여부와 피해 정보를 `PlayerController.TakeDamage`로 전달합니다. 이 함수는 먼저 `PlayerCombat.TryGuard`에 판정을 맡깁니다. 패리 구간이고 해당 공격이 패리 가능하면 패리 성공 이벤트를 발생시키고 체력 피해를 막습니다. 패리 구간이 아니거나 패리할 수 없는 공격은 가드 가능 여부를 확인해 스태미너 피해를 먼저 적용합니다. 스태미너가 남으면 가드가 성공하지만, 해당 타격으로 스태미너가 파괴되면 가드 실패를 반환해 같은 공격이 체력 피해 처리로 이어집니다. 이렇게 전투 판정과 실제 체력 피해 처리를 나누어, 스태미너 파괴 때만 가드가 풀리고 피격 처리가 진행되도록 구성했습니다.”

**설명할 때 잡을 흐름:** `OnGuard 입력 → PlayerGuardState 진입 → 패리 타이머 → TryGuard 판정 → 스태미너 또는 체력 피해`

**관련 코드:** `PlayerController.OnGuard`, `PlayerController.TakeDamage`, `PlayerGuardState.Enter`, `PlayerGuardState.ParryTimerAsync`, `PlayerCombat.GuardStart`, `PlayerCombat.TryGuard`, `PlayerStats.TakeStaminaDamage`

#### 3-b. 적 행동은 FSM과 Behavior Tree를 어떻게 나누어 구성했나요?

“일반 적은 대기, 순찰, 추적, 공격, 경직처럼 상태가 분명한 기본 행동을 FSM으로 관리합니다. 엘리트와 보스는 공격 종류가 많고 상황별 우선순위가 필요해 Behavior Tree를 사용했습니다. 보스의 행동 트리는 `Bandit_Boss.BuildPhase1BT`와 `BuildPhase2BT`에서 단계별로 구성하고, 체력 조건은 `BossController`가 확인해 해당 페이즈 트리로 전환합니다.

트리의 말단인 `ActionNode`는 사거리 확인, 쿨타임 확인, 스킬 실행 같은 실제 함수를 실행합니다. `SequenceNode`는 자식 노드를 차례로 실행하다가 하나라도 성공이 아니면 그 결과에서 멈춥니다. 그래서 ‘사거리 안인가 → 스킬을 쓸 수 있는가 → 스킬 실행’처럼 모두 통과해야 하는 행동을 묶습니다. `SelectorNode`는 자식들을 순서대로 확인해 실패하지 않은 첫 행동을 선택합니다. 보스는 회피, 점프, 단검, 돌진, 근접 공격, 추적, 대기 순으로 확인하도록 구성되어 앞쪽 행동에 더 높은 우선순위를 둡니다. 실행기는 루트를 매 프레임 다시 평가하고, 보스가 사망하거나 행동이 취소되면 전달된 취소 토큰으로 실행을 멈춥니다.”

**설명할 때 잡을 흐름:** `상태/페이즈 확인 → Selector가 우선순위 선택 → Sequence가 조건 확인 → ActionNode가 스킬 실행`

**관련 코드:** `EnemyStateMachine`의 일반 적 상태들, `EliteEnemyController`, `BossController.BuildCombatBT`, `BossController.TakeDamage`, `Bandit_Boss.BuildPhase1BT`, `Bandit_Boss.BuildPhase2BT`, `ActionNode.cs`의 `ActionNode`·`SequenceNode`·`SelectorNode`, `BehaviorTreeRunner.Run`

#### 3-c. 유물은 어떻게 획득하고 효과를 적용하나요?

"보물 상자를 열면 `TreasureObject`가 상자 데이터의 등급별 가중치를 받아 `ArtifactSystem.TryRollRarity`를 호출합니다. 이때 해당 등급에서 아직 드롭하지 않은 유물이 있는지 먼저 확인하고, 가능하면 최소 등급 이상에서 뽑습니다. 조건에 맞는 유물이 없을 때는 더 낮은 등급까지 후보를 넓혀 확인합니다. 등급이 정해지면 `TryGetRandomArtifactData`가 해당 등급의 미드롭 유물 중 하나를 무작위로 고릅니다. 픽업 오브젝트 생성에 성공하면 그 ID를 `HashSet<int>`에 기록해 이후 중복 드롭을 막습니다.

선택 결과는 `ItemFactory`가 ID에 대응하는 런타임 아이템 객체로 만들고, `ArtifactSystem.CreateArtifact`가 `ArtifactDataReader`에서 같은 ID의 `ArtifactData`를 찾아 객체에 초기화합니다. 만들어진 아이템은 월드의 픽업 오브젝트에 전달되고, 플레이어가 획득하면 인벤토리에서 관리됩니다. 장착 시에는 유물의 효과가 플레이어 능력치나 전투 이벤트와 연결됩니다. 예를 들어 `SealOfJudgement`는 장착 중 `OnParrySucceed`와 `OnAttackEnded`를 구독합니다. 패리에 성공하면 능력치 변경을 적용하고 3초 타이머를 시작하며, 시간이 끝나거나 일반 공격이 끝나면 변경한 능력치를 제거합니다. 장착 해제 때는 이벤트 구독과 대기 중인 타이머도 정리합니다. 즉, 데이터는 유물의 설정을 제공하고 런타임 유물 객체는 그 설정에 맞춰 플레이어 시스템과 상호작용합니다.”

**설명할 때 잡을 흐름:** `상자 등급 가중치 → 미획득 유물 선택 → ID로 아이템 생성 → ArtifactData 연결 → 장착 이벤트 구독 → 효과 적용·해제`

**관련 코드:** `TreasureObject`, `ArtifactSystem.TryRollRarity`, `ArtifactSystem.TryGetRandomArtifactData`, `ArtifactSystem.CreateArtifact`, `ArtifactSystem.MarkArtifactDropped`, `ItemFactory.Create`, `SealOfJudgement.OnEquip`, `SealOfJudgement.FirstDamageUp`, `SealOfJudgement.FirstDamageDown`

#### 3-d. 스테이지 생성은 어떤 방식이며, 왜 이 구조를 사용했나요?

“저희 스테이지 지도는 왼쪽에서 오른쪽으로 진행합니다. `floorCount`는 시작 방부터 보스 방까지 가로로 몇 단계가 있는지, `laneCount`는 각 단계에서 방을 놓을 수 있는 세로 위치가 몇 개인지 정합니다. `pathCount`는 시작점에서 보스까지 이어지는 무작위 경로를 몇 개 만들지 정합니다. 그래서 `laneCount`가 9라고 해서 각 단계에 방이 반드시 9개 생기는 것은 아닙니다. 경로들이 같은 위치를 지나면 그 위치의 방 노드를 공유하기 때문입니다.

`StageMapGenerator.Generate`는 먼저 시작 방과 보스 방을 가운데 위치에 두고, 각 경로를 `CreatePath`로 만듭니다. 경로는 한 단계 이동할 때 같은 세로 위치에 머물거나 한 칸 위·아래로 이동합니다. 다음 고정 위치까지 남은 단계 안에 도달할 수 있는 후보만 `GetNextLane`에서 남긴 뒤 그중 하나를 무작위로 고릅니다. 이 제한을 둬 경로가 엘리트 방이나 보스 방에 도달하지 못하는 상황을 막습니다. 엘리트 방은 지정된 단계의 가운데 위치로 모이게 하고, 마지막 단계도 보스 방의 가운데 위치로 연결합니다.

여러 경로를 만든 뒤에는 `(단계, 세로 위치)`를 `Vector2Int`로 표현하고, 이를 키로 하는 `Dictionary<Vector2Int, StageMapNodeData>`에서 방 노드를 찾습니다. 같은 좌표가 이미 있으면 새 방을 만들지 않고 기존 노드를 반환해 경로가 합쳐집니다. 좌표가 처음 나오면 방 노드를 만들고, `nextNodeIds`에 다음 방 ID를 저장합니다. 이후 일반 방 노드 중 일부를 무작위로 골라 보물방과 상점으로 지정하며, 보물방은 가능한 한 서로 다른 단계에 배치합니다. 지도 화면은 노드와 연결 정보를 사용하며, 방을 클리어한 뒤에는 현재 노드의 `nextNodeIds`에 등록된 방만 다음 선택지로 보여줍니다.

이 방식을 택한 이유는 방을 무작위로 흩뿌리면 시작점에서 보스까지 이어지지 않거나 도달할 수 없는 방이 생길 수 있기 때문입니다. 먼저 완주 가능한 경로를 만들고, 같은 위치의 노드를 합치면 연결이 보장된 갈림길과 합류 지점을 만들 수 있습니다. 별도의 복잡한 그래프 생성 알고리즘을 가져오기보다, 가로 진행·제한된 세로 이동·경로 공유라는 게임 규칙을 코드로 직접 표현해 결과를 조절하기 쉽게 했습니다. 이는 특정 표준 알고리즘 이름을 적용한 것이 아니라 프로젝트 규칙에 맞춘 경로 생성 방식입니다.”

**주요 변수는 이렇게 설명하면 됩니다:** `floorCount`는 시작 방부터 보스 방까지의 가로 진행 단계 수, `laneCount`는 단계마다 방을 배치할 수 있는 세로 위치의 범위, `pathCount`는 시작점부터 보스까지 이어지는 경로를 생성하는 횟수입니다. `eliteFloor`는 엘리트 방을 둘 가로 단계이며, 그 단계의 가운데 세로 위치에 배치되도록 경로를 모읍니다. 생성할 때 시작 방과 보스 방은 제외하도록 유효 범위 안으로 보정합니다. 경로가 합쳐지므로 실제 방 개수는 경로 수와 같지 않습니다.

`CreatePath`는 이 경로 하나를 만드는 함수입니다. 먼저 시작 방을 가운데 세로 위치에 넣고, 그 다음 단계부터 한 칸씩 앞으로 이동하면서 방의 세로 위치를 정합니다. 엘리트 단계에 도착하면 위치를 가운데로 고정합니다. 엘리트 단계 전에는 그 가운데에 도달할 수 있는 위치만, 엘리트 단계 후에는 보스 방의 가운데에 도달할 수 있는 위치만 후보로 삼습니다. 후보 위치는 현재 위치에서 같은 줄 또는 바로 위·아래 한 줄이며, 남은 단계 수 안에 목표 위치까지 갈 수 있는지도 확인한 뒤 하나를 무작위로 고릅니다. 마지막에는 가운데 위치의 보스 방을 경로에 추가합니다.

쉽게 말하면, **“시작점에서 한 단계씩 랜덤하게 움직이되, 엘리트 방과 보스 방에 제때 도착할 수 있는 방향만 고르는 방식”**입니다. 예를 들어 가운데 줄에서 출발해 위쪽으로 움직였더라도 엘리트 단계까지 남은 이동으로 가운데에 돌아올 수 있어야 그 경로를 허용합니다. 이렇게 해서 경로 모양에는 무작위성을 주면서도 엘리트와 보스까지 이어지도록 합니다.

**설명할 때 잡을 흐름:** `완주 가능한 경로 생성 → 같은 좌표의 방 노드 공유 → 다음 방 ID 연결 저장 → 클리어 후 연결된 방 선택`

**관련 코드:** `StageMapGenerator.Generate`, `StageMapGenerator.CreatePath`, `StageMapGenerator.GetNextLane`, `StageMapGenerator.GetOrCreateNode`, `StageMapNodeData.nextNodeIds`, `StageManager`, `RoomSystem`

#### 3-e. 다른 방식도 가능한데 왜 이 방식을 선택했나요?

“기능만 보면 다른 방식도 가능하지만, 프로젝트에서 필요한 데이터 흐름과 변경 단위를 기준으로 선택했습니다. 예를 들어 패리 시간은 가드 상태와 함께 끝나야 하므로 상태의 취소 토큰과 연결했습니다. 보스는 행동 후보가 많아 우선순위와 조건 검사를 트리로 나눴습니다. 유물은 상자 보상과 장착 효과를 분리해 ID와 데이터로 연결했습니다. 스테이지는 완주 가능한 경로를 먼저 만들고 같은 좌표를 합쳐, 갈림길과 합류를 만들면서도 보스까지의 연결을 보장했습니다. 각각 장점만 있는 것은 아니므로, 상태가 복잡해지거나 이벤트 추적이 어려워지는 부분은 생명주기와 연결 정보를 함께 관리했습니다.”

#### 3-f. 선택한 방식의 단점이나 주의점은 무엇인가요?

“Behavior Tree는 노드를 분리해 우선순위를 보기 쉽지만, 노드가 늘면 실행 순서와 조건을 따라가야 합니다. 이벤트 방식의 유물 효과는 장착 해제 때 구독을 빼먹으면 효과가 남거나 중복 적용될 수 있어 구독 해제와 타이머 취소를 함께 처리합니다. 스테이지 경로는 `pathCount`를 늘려도 경로가 합쳐지므로 실제 방이 그 수만큼 늘지는 않습니다. 또한 세로 위치 이동을 한 단계에 한 칸으로 제한하므로 이 규칙에 맞는 경로만 생성됩니다. 면접에서는 이런 제약을 숨기기보다 현재 구조가 보장하는 점과 제한하는 점을 구분해 설명합니다.”

### 4. 작업한 부분에서 개선하고 싶은 부분과 그 방법은?

개인 프로젝트에서는 시스템이 추가될수록 기능 간 연결과 데이터 검증을 더 명확히 드러내고 싶습니다. 우선 반복적으로 변경되는 데이터의 입력 오류를 조기에 찾을 수 있도록 검증과 오류 메시지를 보강하고, 기능별 의존 관계와 생명주기 처리 기준을 문서화하겠습니다. 실제 개선을 진행하지 않은 항목은 이미 구현한 결과처럼 말하지 않고 향후 개선 계획이라고 구분합니다.

### 5. 서버개발자 혹은 기획자와의 협업 경험 있는지

5인 팀 프로젝트에서 기능을 연동하기 위해 팀원들과 이벤트 종류와 전달 데이터, 적용 순서를 논의한 경험이 있습니다. 서버 개발자나 기획자와 직접 협업한 경험은 본인 사실에 맞춰 답해야 합니다. **직접 협업하지 않았다면:** “서버 개발자와 직접 협업한 경험은 아직 없습니다. 팀 프로젝트에서는 다른 담당자의 기능을 연결할 때 이벤트 계약과 데이터 형식을 맞추며 협업했습니다.”

## 4. 기타

### 1. 자기소개(1분 정도 분량)

안녕하세요. 기능이 실제 플레이에서 어떻게 연결되는지와 변경에 따른 영향을 함께 고려하는 게임 클라이언트 개발자 지원자입니다. 5인 팀 프로젝트에서는 날짜·이벤트·자동 생산 시스템과 디버그 도구를 담당했고, 매니저 간 직접 참조를 줄이기 위해 공통 이벤트 구조를 제안하고 팀에 적용했습니다. 개인 프로젝트 Shield Hero에서는 전투와 유물, 스테이지 생성 시스템을 구현했으며, 공격 판정의 메모리 할당을 프로파일러로 측정해 개선한 경험이 있습니다. 문제를 추측으로 끝내지 않고 원인을 확인하고 검증하는 태도를 바탕으로 플레이 감각과 안정성을 갖춘 기능을 만드는 개발자로 성장하고 있습니다.

### 2. 지원 동기

게임은 사용자의 입력이 화면과 플레이 경험으로 즉시 이어지는 소프트웨어라는 점에 매력을 느껴 게임 클라이언트 개발을 선택했습니다. 전투 판정, UI, 상태 처리처럼 작은 구현 차이가 조작감과 게임의 완성도에 영향을 주는 점에 관심이 있습니다. 프로젝트를 진행하며 기능 구현뿐 아니라 시스템 간 연결과 성능 확인도 중요하다는 것을 경험했고, 이런 부분을 계속 배우며 게임 플레이에 직접 기여하는 개발자가 되고 싶습니다.

### 3. (비전공자라면) 이 업계로 온 이유

전공 여부가 확인되지 않았으므로 해당되는 경우에만 사용합니다. “전공과 별개로 프로그래밍을 학습하며, 입력과 로직의 결과가 플레이 경험으로 바로 드러나는 게임 클라이언트 개발에 관심을 갖게 됐습니다. C#과 Unity로 기능을 직접 구현하고 문제를 수정하는 과정에서 이 분야를 진로로 구체화했습니다.” 본인의 실제 학습 계기와 전공을 바탕으로 수정합니다.

### 4. (타 직종 근로 경험이 있다면) 이 업계로 옮긴 이유

이전 직종 경험이 있는 경우에만 답합니다. “이전 업무를 통해 [실제로 얻은 역량]을 쌓았고, 이후 [게임 개발을 선택하게 된 구체적인 계기]를 경험했습니다. 관심에 그치지 않고 [학습·프로젝트·포트폴리오 등 실제 행동]으로 진로를 준비했고, 그 경험을 바탕으로 게임 클라이언트 개발 직무에 지원했습니다.”

### 5. (있다면) 기존 회사를 그만둔 이유

실제 이직 경험이 있는 경우에만 답합니다. 이전 회사나 동료를 비난하기보다, 이직을 고민한 배경과 다음 직무를 선택한 기준을 설명합니다. “당시 [사실에 기반한 이유]를 계기로 다음 경력을 고민했고, 제가 장기적으로 전문성을 쌓고 싶은 방향이 [지원 직무]라는 점을 확인했습니다. 이를 위해 [실제로 한 준비]를 진행했습니다.”

### 6. (있다면) 공백 기간에 무엇을 했는지

공백이 있는 경우에만 답합니다. 해당 기간에 실제로 한 학습·개인 프로젝트·구직 준비·생활상 사유를 시간 순으로 간단히 설명하고, 현재 업무에 활용할 수 있는 준비를 덧붙입니다. 사실과 다른 공부나 성과를 만들어 넣지 않습니다.

### 7. 야근이 많은데 괜찮은지

“프로젝트 마감이나 장애 대응처럼 필요한 상황에서 팀과 우선순위를 맞춰 대응할 수 있습니다. 다만 지속적인 야근이 기본 전제가 되기보다 일정과 위험을 조기에 공유해 안정적으로 목표를 달성하는 것이 중요하다고 생각합니다. 업무 상황을 투명하게 공유하고 필요한 대응에 책임 있게 참여하겠습니다.”

### 8. 프로젝트 중 팀원과 마찰이 생긴다면 어떻게 할 것인지

“먼저 의견 차이가 기술적 기준, 일정, 역할 중 어디에서 생겼는지 확인하겠습니다. 각 선택지의 영향과 근거를 정리해 팀 목표에 더 적합한 방법을 논의하고, 결정된 기준과 담당 범위를 공유하겠습니다. 에셋 누락 문제를 함께 해결했을 때도 각자 프로젝트 구성을 비교하고 가설을 확인하며 원인을 좁혔습니다.”

### 9. 우리 회사 게임을 해 보았는지

지원 회사의 게임을 실제로 플레이한 뒤에만 답합니다. “최근 [게임명]을 플레이했습니다. 특히 [직접 경험한 전투·조작·성장 요소]가 인상적이었고, [구체적인 장면이나 시스템]에서 그렇게 느꼈습니다. 플레이 경험을 통해 [지원 직무와 연결되는 관찰]을 했습니다.” 플레이하지 않은 게임을 했다고 말하지 말고, 지원 전 실제로 경험한 뒤 구체적인 내용을 채웁니다.

### 10. 평소 어떻게 공부하는지

“먼저 해결하려는 문제를 작게 나누고 공식 문서와 신뢰할 수 있는 자료를 확인합니다. 간단한 코드로 동작을 재현하고, 예상과 결과가 다르면 로그나 프로파일러를 이용해 원인을 확인합니다. 학습한 내용은 프로젝트에 작은 범위로 적용해 보고, 동작 원리와 한계를 설명할 수 있도록 정리합니다.” 본인이 실제로 쓰는 학습 루틴에 맞게 조정합니다.

### 11. 프로그래머로서 가장 중요한 것은 무엇이라고 생각하는지

“요구사항을 정확히 이해하고, 동작을 근거로 확인하는 태도가 중요하다고 생각합니다. 코드는 기능을 만드는 수단이므로 현재 요구를 해결하는 동시에 다른 기능과의 연결, 변경 시 영향, 오류 확인 방법도 고려해야 합니다. 성능 문제도 추측으로 단정하지 않고 측정 결과로 확인해야 합니다.”

### 12. 게임에서 가장 중요한 것은?

“플레이어가 의도한 입력에 게임이 일관되고 명확하게 반응하는 것이 중요하다고 생각합니다. 규칙과 피드백을 이해하기 쉽고 조작 결과를 예측할 수 있어야 몰입할 수 있습니다. 이를 위해 클라이언트 기능은 판정의 정확성뿐 아니라 입력 반응, 애니메이션·효과와의 연결, 프레임 안정성을 함께 고려해야 합니다.”

### 13. 본인의 강점은?(지원자를 채용해야 하는 이유는?)

“문제가 생겼을 때 처음 떠오른 원인을 그대로 가정하지 않고, 정상 동작과 문제 상황의 차이를 비교해 검증하는 편입니다. 팀 프로젝트의 에셋 문제에서는 두 프로젝트 구성을 대조해 누락된 에셋을 찾아냈고, 개인 프로젝트에서는 Profiler로 공격 탐색의 할당을 확인하고 변경 전후를 같은 조건에서 비교했습니다. 맡은 기능을 구현하는 데서 멈추지 않고 원인과 결과를 확인하는 점이 제 강점입니다.”

### 14. 능력 있고 인성이 별로인 팀장 vs 능력 없지만 천사표 팀장 1택과 그 이유

“둘 중 하나를 그대로 선택하기보다, 팀의 목표를 달성하면서 신뢰를 지킬 수 있는 리더십이 필요하다고 생각합니다. 전문성은 올바른 판단과 팀 지원에 중요하고, 존중과 소통은 구성원이 문제를 공유하고 협업하는 기반입니다. 둘 중 하나만 부족한 상황이라면 업무 목표와 영향에 따라 보완 가능성을 판단하겠지만, 지속적인 무례함이나 책임 회피는 팀 성과에도 해롭다고 봅니다.”

### 15. 불합리한 업무 배정을 받는다면 어떻게 할 것인가

“우선 업무의 목적과 마감, 우선순위, 제가 맡아야 하는 범위를 확인하겠습니다. 기존 업무와 충돌하거나 일정상 위험이 있으면 예상 소요와 영향을 근거로 공유하고, 우선순위 조정이나 범위 조정 방안을 제안하겠습니다. 최종 결정이 내려지면 합의된 우선순위에 따라 진행 상황과 위험을 계속 공유하겠습니다.”

### 16. 가장 최근 공부한 내용과 설명

“최근에는 [실제로 공부한 주제]를 학습했습니다. [핵심 개념]을 확인하고, [문서·예제·작은 구현]으로 동작을 검증했습니다. 그 결과 [배운 점 또는 적용 가능성]을 이해했습니다.” 현재 실제로 공부한 내용을 입력해야 합니다. 최근 학습을 진행한 뒤 답변을 완성하세요.

### 17. 현재 하고 있는 것(공부, 포트폴리오용 프로젝트, 외주, 인디 팀 등)

“현재 개인 프로젝트 Shield Hero의 기술 문서와 README를 정리하고 면접 대비를 하고 있습니다. 프로젝트에서 구현한 전투, 유물 데이터, 스테이지 생성 구조를 코드와 실제 에셋 화면에 대응해 설명할 수 있도록 정리하고 있습니다. 추가 개발이나 다른 활동이 있다면 현재 사실에 맞게 덧붙이겠습니다.”

### 18. (대졸이라면) 학부시절 배운 것, 수업 외 활동, 기억에 남는 일 등

학력과 대학 경험이 확인되지 않았으므로 해당되는 경우 본인의 사실로 작성합니다. “학부에서 [관련 과목·기초]를 배웠고, 수업 외에는 [실제 프로젝트·동아리·활동]을 했습니다. 그중 [구체적인 문제나 역할]을 경험하며 [배운 점]을 얻었고, 현재 게임 클라이언트 개발을 준비하는 데 [어떻게 연결되는지] 활용하고 있습니다.”

## 면접 전 최종 점검

- “사용했다”라고 말한 기술은 어디에 어떤 목적으로 썼는지 설명할 수 있는지 확인합니다.
- 성능 수치에는 측정 조건과 비교 기준을 함께 말합니다.
- 본인 기여와 팀 전체 결과를 구분합니다.
- 모르는 질문에는 아는 범위와 확인이 필요한 부분을 나눠 답합니다.
- 회사·학력·근무 이력 질문은 실제 경험으로 빈칸을 채웁니다.
- 각 답변을 소리 내어 30~60초 안에 설명해 보고, 추가 질문에도 코드나 근거로 답할 수 있게 준비합니다.
